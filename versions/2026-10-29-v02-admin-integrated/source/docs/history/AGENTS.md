# 项目共同工作规则

## 用户要求

如果用户指令与 skills 工作流冲突，一切以用户的指令为准。保持独立判断，禁止默认用户观点正确；发现矛盾应说明依据，必要时询问，同时继续不依赖答案的工作。

本项目由用户一人推进，Codex 与 DSH 在不同对话协作。用户负责教学要求、账号和最终验收。当前目录是正式代码与任务资料的根目录，不要把上一级 HTML 方案页当成教学系统源码。

## 范围与目录

- 首版：跨设备网页，文字问答、班级、自动评价、基础图表、教师复核、导出和基础备份。
- 最多300人同时在线并集中提交，运行一年，经费约5000元；全年学生总数、题量仍待确认。
- 技术基线：React + TypeScript + Vite 前端，Node.js + TypeScript 后台，CloudBase为优先评估的部署方案。具体兼容版本在真实环境检查后锁定，不从旧对话猜测版本。
- `frontend/` 与 `backend/` 是各自独立的 npm 包，各自维护 package.json 和 lock 文件。首版不建立根目录 npm workspaces，避免两边同时改同一锁文件。公共类型从 `shared/contracts.ts` 引用，构建包含方式需实际验证。
- DSH负责 `frontend/`、自己的接续和交付文件；Codex负责 `backend/`、共享契约、集成和上线资料。需要修改对方文件时先在交接文件说明，待交接后由集成方修改。
- 不擅自发明学科题目、正式评分维度、权重、参考答案或教学有效性结论。演示数据显式标为模拟。
- 不建立收费、音视频、监考、社交等额外模块。必要的账号、权限与可靠提交不能因界面简化而省略。

## 长对话接续：双方必须遵守

1. 不把聊天历史作为唯一状态存储。Codex更新 `handoff/CODEX_CONTINUE.md`，DSH更新 `handoff/DSH_CONTINUE.md`。
2. 如果能看到上下文用量，在已用约70%或剩余约30%时立即更新接续文件；若无法读取准确比例，不得伪称能监测，改为每完成一阶段、每约10次实质性工具操作、重大设计变更或出现阻塞时更新，以先到者为准。
3. 准备换对话、对话明显变长、收到上下文压缩提示时，优先保存接续文件，不等压缩后凭印象重建。
4. 文件须写明已完成/未完成、实际文件、启动方式、契约版本、已执行验证与证据、已知错误、未决事项、下一步，以及新对话启动语。只记录密钥变量名，不记录密钥、口令、访问令牌或学生敏感信息。
5. 保存后明确告诉用户接续文件路径，用户自行新开对话。不要自动新建聊天，也不要只在聊天里输出摘要而不保存文件。
6. 接续文件记录的结果在新对话中需与实际文件核对；不要把未运行的检查改写成“通过”。

## 验证与完成边界

- 先读实际代码、共享契约和自己的接续记录，再修改；保留已有用户修改。
- 使用成熟身份认证或经过验证的库，不自行设计密码加密或把演示账号带入生产。
- 提交成功以数据库确认保存为准；评分任务需要持久化、幂等与失败重试，不能只在浏览器或进程内保存队列。
- 所有角色和班级权限由服务端判断。学生不得获取他人答卷，教师不得获取非授权班级数据。
- 无评分规则时显示“待配置评价体系”，不能伪造正式得分。
- 浏览器模拟手机宽度不等于真机验证；模拟接口不等于联网；套餐标称额度不等于300人业务压测通过。
- 不默认付费、购买域名、改动账号配置或对外发布；先准备可检查的方案和代码，涉及实际支出或外部发布按用户已有授权及工具权限执行。
- 中间文件放各模块的 `work/`，验证记录放各自 `verification/`，不要将真实数据或密钥写入共享交付。
