# 两位Codex用户通过GitHub协作

## 分工和状态

本机负责人/Codex维护backend、shared、integration、部署与整体验收；同事/Codex维护frontend及前端接续/交付单。已有本地集成源码，不重建。原DSH交付作为历史保留。

仓库公开意味着任何人能读取和Fork，并不意味着所有人能直接推送主仓库。没有写入权限也能通过Fork与PR参与；需要直接推送时，由仓库所有者在设置中添加明确的协作者。

## 首次开始

1. 克隆主仓库到自己的电脑；没有写入权限的同事先Fork，克隆自己的Fork并添加原仓库为upstream。
2. 阅读README、AGENTS和自己任务书，再读当前接续记录。旧绝对路径是历史机器信息，实际以克隆目录为准。
3. frontend/backend各自npm ci；不上传依赖、dist、work、数据库、账号或.env私密配置。后端账号按受控命令在各自本机创建。
4. 在新任务分支工作，例如backend/rubric-adapter或frontend/mobile-review。不要两人同时改同一任务分支。

## 一轮修改

先同步main，再建任务分支。只修改自己负责的模块，运行相关检查，更新自己的接续/交付文件并提交。不要在有未保存修改时盲目pull、reset或clean；先查看git status并保留修改。不要强推共享分支。

有写入权限：把分支推送主仓库并提PR。无权限：推送到自己的Fork，向原仓库main提PR。PR描述需要问题、改动、验证、契约版本和未完成项。由本机负责人审阅后合并；发生冲突时按当前契约解决，不用“全部接受一边”覆盖另一人改动。

## 共享接口

shared归本机负责人统一维护。前端若需新字段，在PR/FRONTEND_DELIVERY里说明接口、字段、用途和兼容性，待契约变更后适配。两端各自维护独立package-lock，不建立根workspaces，不跑全仓无关格式化或升级。

## 换对话和交接

本机：handoff/CODEX_CONTINUE.md；同事：handoff/FRONTEND_CONTINUE.md。保存当前阶段、分支、文件、验证、问题和下一步，与代码一并提交分支。准确上下文可见时70%已用/30%剩余提前保存；否则按阶段/约10次实质操作更新，不假装精确监测。新对话先读记录并核对文件。

## 当前不应宣称的结果

GitHub同步不代表网站已部署。正式评分、云配置、300人集中提交、真机试用和一年云运维仍待完成；本地验证范围见证据。公开仓库不得提交真实学生资料、密钥、会话或本地数据库。

## GitHub网页常用位置

- Code：源码、README与下载ZIP。
- Pull requests：审阅和合并任务分支。
- Fork：无主仓库写入权限时开始贡献。
- Settings / Collaborators：所有者添加协作者。

以上为协作流程约定，尚不表示已设置强制分支保护、CI或自动部署。不要自动开通Pages作为正式教学后台。
